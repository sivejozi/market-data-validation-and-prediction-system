Part one · The problem

Market data is small, and it has to be right

  • Exchange rates and interest rate fixings, published daily
  • A customer is quoted off a bad rate — and accepts itThat deal is binding. Nobody unwinds it in the morning because the feed was wrong.
  • Everything downstream consumes it: pricing, risk, regulatory reporting, trading
  • One wrong rate propagates into every valuation that runs that night
6,417
daily observations for one currency pair, 2000–2025
4
instruments, two independent data providers
This is kilobytes, not terabytes. The engineering problem is not volume — it is knowing whether a number is correct.
Part one · The problem

How this is actually done today

  • Static rules“Reject if it moved more than 5% from yesterday.” Cheap, and wrong in both directions.
  • Human reviewSomeone scans a spreadsheet each morning. Does not scale, and does not run at 2am.
  • Post-hoc reconciliationYou find out on Thursday that Tuesday was wrong.
A 5% threshold cannot distinguish a bad feed from a currency crisis. In March 2020 the correct answer was “yes, the market really moved that much”.

Part one · The pipeline

Why an event bus, and not just an API call?

A topic is an append-only log

  • Producers write to it. Consumers read from it at their own pace.
  • Neither knows the other exists.

What that buys you

  • Add a consumer without touching the producerThe alerting service was added last. The preprocessor never changed.
  • Consumers can fail independentlyIf the database is down, messages wait. Nothing is lost.
  • You can replayRebuild a downstream store by reading the log again.
Part one · The pipeline

One service computes features. Once.

Computed once, in the preprocessing service, and stored on the record — so every model sees identical numbers, and one definition change propagates to all six. The alternative fails quietly: two services each compute a seven-day mean, one includes today and one does not, and both look correct until a report disagrees six months later.
Part one · Method

What do you do when there are no labels?

  • Nobody hands you labelled anomaliesThere is no column marked “this rate was wrong”. So the clustering stage manufactures one.
  • The classifier makes scoring cheapRecomputing centroid distances needs the full history. A saved classifier does not.
But a model trained on another model’s output is not an independent opinion — and my escalation rule needs two votes of three. Hold that thought. The numbers are in part two.

Same pipeline, same cluster — and the machine learning service takes nine times longer to deploy than the Java one. Its image installs NumPy, pandas, scikit-learn and TensorFlow; the Java one is a single JAR. The modelling stack you choose quietly sets how fast you can ship a fix.
Part two · Prediction result

The simplest model won

A tree predicts by averaging the training values in a leaf — so it cannot output a number it has never seen. SOFR went from near zero to over five percent, and both tree models were trapped below it. R² measured on levels — and “tomorrow equals today” scores about as well. These numbers describe the data more than the models.
Part two · Validation result

Three detectors, three different answers

Rows one and three track each other because one is trained on the other’s output. Only the middle row is independent — and it caught COVID on both currency pairs when clustering did not, and the September 2019 repo crisis at 21× its threshold, alone. My rule escalates on two votes of three. It would have discarded the best detection the system ever made.
Part two · What a dealer gets

Two answers, at the moment of the quote

  • A value to check the quote againstAn expected rate and the deviation from it. A reference point — not a forecast to trade on.
  • A verdict with a reason attachedWhich detectors flagged it, and how strongly. A dealer sees why, not just a refusal.
  • Before the quote, not after itThe difference between catching a bad rate and explaining one the next morning.
Back to the customer on the first slide — this is where that deal stops being binding on a wrong number.

Getting your first job

What to learn, what to build, and how to talk about it.

Part three · Skills

The short list that actually matters

  • SQL, properlyJoins, window functions, query plans, indexes. Not “I have used SELECT”.
  • One language wellPython is fine. Well means testable, packaged, and readable by someone else.
  • Git, and CIBranches, reviews, and a pipeline that runs your tests automatically.
  • ContainersEnough Docker to package your own work and explain what an image is.
  • One cloud, one orchestratorDepth in one beats a list of six. The concepts transfer.
  • How data actually movesBatch versus streaming, idempotency, schema change, late-arriving data.
Part three · What to build

Somewhere that is not your laptop.
  • Scope it deliberately smallOne source, one table, one view. Finished beats ambitious.
  • One finished project beats five notebooksBecause only the finished one forces you to handle failure, scheduling and deployment — which is the actual job.
Part three · What to build

Make the unglamorous parts visible

  • A schema, with constraints
  • Tests that run in CI
  • Ingestion you can safely run twice
  • A README with a diagram
  • One honest “known limitations” section
Anyone can train a model. Very few graduates can show me ingestion that is safe to re-run, or a constraint that prevents a class of bug. That is what separates a project from a portfolio piece.
Part three · Interviews

How to talk about what you built

  • The problemIn one sentence, without jargon.
  • The constraintNo budget, no labelled data, one week. Constraints make choices sound deliberate.
  • What you chose, and what you rejected“I used Postgres over a queue because…” This is the part they are assessing.
  • What brokeHave one real failure ready. Mine is the model that gave a different answer on the same data.
  • What you would do differentlyShows you learned something rather than just finished something.
Part three · Which path

Data engineering or data science?

Data engineeringData science
Optimises forCorrectness, reliability, costInsight, inference, decisions
Day to dayPipelines, schemas, orchestration, on-callQuestions, models, analysis, communication
Judged onDid the data arrive, correct and on timeWas the conclusion right and did it change anything
SharedSQL, Python, version control, and a great deal of “is this number actually right?”
You do not have to choose now. Build the pipeline either way — a data scientist who can deploy is rare, and a data engineer who understands models is rarer.
Part three · Learning

Where to actually learn this

  • Official documentation, not coursesFor Docker, Kafka, Kubernetes and Postgres the docs are better and current. Courses go stale.
  • One book per area, read properlyFor this field, Kleppmann’s Designing Data-Intensive Applications is the one.
  • Build first, then readReading about partitioning before you have hit a partitioning problem does not stick.
  • Read other people’s codePick a small open-source project and follow one pull request end to end.
Part three · This week

Three things you can start now

  • Pick one public API and ingest it on a scheduleInto a real database, with a unique constraint so re-running is safe. One evening.
  • Put it in Git with a test and a CI workflowEven one test. The habit matters more than the coverage.
  • Write the README as though a stranger will run itBecause in an interview, one will.
