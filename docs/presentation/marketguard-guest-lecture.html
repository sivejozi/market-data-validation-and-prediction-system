Part one · The problem

The risk is not data volume. It is a wrong number.

  • Exchange rates and interest rate fixings, published daily
  • A customer is quoted off a bad rate — and accepts itThat deal is binding. Nobody unwinds it in the morning because the feed was wrong.
  • Everything downstream consumes it: pricing, risk, regulatory reporting, trading
  • One wrong rate propagates into every valuation that runs that night

The dataset is modest. The consequence of accepting a bad value is not.
Part one · The problem

Why fixed rules are not enough

  • A fixed percentage catches some errors and flags genuine market moves.“Reject if it moved more than 5% from yesterday.” Cheap, and wrong in both directions.
  • Useful context, but slow, inconsistent and difficult to scale.Someone scans a spreadsheet each morning. Does not scale, and does not run at 2am.
  • Finding the problem later does not prevent the original decision.You find out on Thursday that Tuesday was wrong.
The core challenge: distinguish a data-quality failure from a genuine market event.

Part one · The pipeline

Why Kafka here? Decoupling and replay

Think of it as a durable stream of records that multiple consumers can read independently.

  • Producers write to it. Consumers read from it at their own pace.
  • Neither knows the other exists.

What that buys you

  • New downstream behaviour can be added without changing ingestion.The alerting service was added last. The preprocessor never changed.
  • A consumer outage need not become a synchronous failure in the producer.If the database is down, messages wait. Nothing is lost.
  • Replay helps rebuild downstream state, provided retention and processing semantics support it.Rebuild a downstream store by reading the log again.
Part one · The pipeline

Feature consistency is a data-quality control

Compute features once and attach them to the record:

instrument, date, rate,
lag1, lag7,
rollingMean7, rollingStd7,
rateScaled

Yesterday’s rate and last week’s, a seven-day mean and standard deviation, and the rate rescaled to zero mean and unit variance — so the model never sees a raw price.

Why seven days: a trading week plus a buffer. It was a choice, not a result — I did not tune it.

  • Consumers share the same feature definition and values.
  • The alternative fails quietlyTwo services each compute a 7-day mean. One includes today, one does not. Both look correct. You find out in a report six months later.
  • Centralisation reduces drift, but changing a feature may require reprocessing historical data.Change a feature definition and you must reprocess. That is a real trade-off, not a free win.
Part one · How it decides

Prediction and anomaly detection answer different questions

  • Prediction asks what the rate should beThree regressors produce an expected value, and the deviation from it is the signal.
  • Validation asks whether it looks familiarThree detectors score the rate against the shape of everything seen before. No target value, just a verdict.
  • Neither alone is enoughA rate can be far from expected and still correct — March 2020. Or close to expected and still wrong.
Part one · Method

Learning without labelled examples

  • Nobody hands you labelled anomaliesThere is no column marked “this rate was wrong”. So the clustering stage manufactures one.
  • The classifier makes scoring cheapRecomputing centroid distances needs the full history. A saved classifier does not.
But a model trained on another model’s output is not an independent opinion — and my escalation rule needs two votes of three. Hold that thought. The numbers are in part two.
Part one · MLOps

Do not retrain a model on every request

My first version retrained the model on every request. Thirty seconds to validate one number. If you take one thing from this slide: never train in a request handler.

The engineering lessons apply beyond this project

A short, practical checklist for turning coursework into demonstrable engineering skill.

Part three · Skills

Build the fundamentals employers can verify

  • SQL, properlyJoins, window functions, query plans, indexes. Not “I have used SELECT”.
  • One language wellPython is fine. Well means testable, packaged, and readable by someone else.
  • Git, and CIBranches, reviews, and a pipeline that runs your tests automatically.
  • ContainersEnough Docker to package your own work and explain what an image is.
  • One cloud, one orchestratorDepth in one beats a list of six. The concepts transfer.
  • How data actually movesBatch versus streaming, idempotency, schema change, late-arriving data.
Part three · What to build

Finish one small system, not five unfinished notebooks

Ingest
A public API on a schedule.
→

A real database with a real schema.
→

Tested, and idempotent.
→

An endpoint or a dashboard.
→
Deploy
Somewhere that is not your laptop.
  • Keep the scope small enough to finishOne source, one table, one view. Finished beats ambitious.
  • Finish the whole lifecycleScheduling, failure handling, storage and deployment are part of the work — not optional extras.
Part three · What to build

Make reliability visible in your portfolio

  • A schema, with constraints
  • Tests that run in CI
  • Ingestion you can safely run twice
  • A README with a diagram
  • One honest “known limitations” section
A strong portfolio shows the work around the code: repeatable ingestion, schema constraints, tests, documentation and an honest account of limitations. That is what separates a project from a portfolio piece.
Part three · Interviews

Tell the story: problem, decision, evidence, failure, lesson

  • The problemIn one sentence, without jargon.
  • The constraintNo budget, no labelled data, one week. Constraints make choices sound deliberate.
  • What you chose, and what you rejected“I used Postgres over a queue because…” This is the part they are assessing.
  • What brokeHave one real failure ready. Mine is the model that gave a different answer on the same data.
  • What you would do differentlyShows you learned something rather than just finished something.

Part three · Learning

Learn by building, then use the documentation to go deeper

  • Official documentation, not coursesFor Docker, Kafka, Kubernetes and Postgres the docs are better and current. Courses go stale.
  • One book per area, read properlyFor this field, Kleppmann’s Designing Data-Intensive Applications is the one.
  • Build first, then readReading about partitioning before you have hit a partitioning problem does not stick.
  • Read other people’s codePick a small open-source project and follow one pull request end to end.
Part three · This week

Three actions you can take this week

  • Pick one public API and ingest it on a scheduleInto a real database, with a unique constraint so re-running is safe. One evening.
  • Put it in Git with a test and a CI workflowEven one test. The habit matters more than the coverage.
  • Write the README as though a stranger will run itBecause in an interview, one will.
